# AI 办公竞品日报（Dify 多 Agent 工作流）

每天自动追踪 **飞书 / 钉钉 / 企业微信** 的 AI 办公动态，生成一份带「对我方产品的启示」的竞品日报，并发送到邮箱。

## 架构

```
定时/手动触发
  → 三路并行：Tavily 搜索（域名白名单）→ 时区转换（代码）→ 分析员 LLM
  → 总编 LLM（合并去重、定 type / importance）
  → 硬规则检查（代码：链接在原始结果中 / 非首页 / 北京日期 == today）
  → 审核员 LLM → 解析审核（代码）
  → IF 通过 → 输出 ；ELSE → 重写 LLM → 变量聚合器
  → 日期标注（代码）→ 模板转换（Jinja）→ 邮件推送
```

- 共用评判标准放在 Dify 环境变量 `daily_rules`（单一事实来源），总编、审核员、重写三个节点都引用它。
- 重要度锚点：5 年度发布会/战略；4 官宣联合/打通/接入、大版本、核心 AI；3 联名硬件、新品、重要功能；2 行业观察；1 小修复。
- 职责分离：日期换算、链接校验、打分等确定性逻辑交给代码节点，LLM 只负责判断和写作。

## 评测方法（Harness）

- **回放评测**：回测副本跳过 Tavily，把搜索结果文本直接作为输入（`fixtures/`），同一输入可以反复跑。
- **合成样本**：`fixture-2026-11-*` 都是虚构的边界用例（空结果日、年度发布会、三家同一天、日期边界），链接统一用 example.com。
- **自动打分**：`nodes/auto-score-node.py` 按样本期望检查条数、收录、type、importance、过滤和禁用词，输出 `score` / `fails`。
- **停止标准**：每个样本跑 3 遍。同一问题 3 次里至少 2 次复现、并且会误导读者才修改；只出现 1 次的波动记进 `docs/error-log.md`，不改。

## 结果

| 样本 | 内容 | 结果 |
|---|---|---|
| 10-12 真实回放 | 安克联名耳机 + 复盘文过滤 | 7/7 ×3 |
| 10-14 真实回放 | 企业微信×WorkBuddy 官宣 | 核心验收 ×3 通过 |
| S1 空结果 | 当天无动态 | 2/2 |
| S2 年度发布会 | 同一事件多篇报道合并 | 7/7 ×3 |
| S3 三家同天 | 含横评干扰 | 7/7、7/7、6/7（单次波动，记录未改） |
| S4 日期边界 | GMT 跨日新闻 / 官网首页 / 旧闻 | 修复前 5/7 ×3 → 修复后 7/7 ×3 |

**S4 案例**：新闻发布时间是 GMT 11-03 23:30，换成北京时间已经是 11-04 07:30，但 LLM 直接拿 GMT 日期去比较，连续 3 次漏收。修法是加「时区转换」代码节点，没有改提示词。第一次只让分析员改读转换后的文本，分数反而掉到 4/7；看 trace 才发现，审核员还在读原始 GMT 文本，把正确收录的条目判成了旧闻。让所有读搜索结果的节点都改读同一份转换后的文本后，3 次都是 7/7。

## 使用

在 Dify 里选「导入 DSL 文件」，选 `dsl/competitor-daily-v6.yml`，然后配置 Tavily、DeepSeek 和邮件插件的凭证，再把发送邮件节点的收件人改成你自己的邮箱。

## 目录

- `dsl/`：Dify 工作流导出文件（收件邮箱已替换为占位）

- `nodes/`：代码节点（时区转换、硬规则检查、自动打分）
- `fixtures/`：回放样本（真实回放 + 合成样本）
- `docs/error-log.md`：错误日志与每次修复的决策记录
